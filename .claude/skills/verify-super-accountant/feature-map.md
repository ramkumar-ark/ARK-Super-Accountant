# Super Accountant feature map

How a user reaches each feature, how an agent drives it over HTTP, and what observable state proves it works. Verified against `main` controllers (GSTR-1 endpoints live in `gstr1/controllers/Gstr1WorkflowController.java`, not the old plan's paths).

| Feature | User path | Agent driving (HTTP) | Proof | Scenario |
|---|---|---|---|---|
| Sign in + roles | /login → JWT per role | `POST /api/auth/signin` as Operator and Accountant; bad password 401; unauthenticated request rejected | 200 + `role` claim matches | `sign-in` |
| Workflow lifecycle | Workflows page → create → advance → finalize/unfinalize; discard started workflow | `POST /api/v1/workflows` {type, periodKey}, `POST /{id}/advance`, `/{id}/finalize`, `/{id}/unfinalize`, `POST /{id}/discard`, `GET /{id}/events` (WorkflowController:71-118) | stage transitions PREPARE→FINALIZED in responses and events; OPERATOR forbidden to advance (403); discard at STARTED marks active:false and unlocks responsibility-start; OPERATOR forbidden to discard (403); discard after stage advance or with data returns 409 | `workflow-lifecycle` |
| GSTR-1 prepare (tables) | Workflow detail → Gstr1PreparePanel | `GET /api/v1/workflows/{id}/gstr1/tables` (Gstr1WorkflowController:104) | 200 object; readable by Operator too | `gstr1-tables` |
| GSTR-1 prepare (fill-ins) | Gstr1PreparePanel fill-in save | `PUT /api/v1/workflows/{id}/gstr1/fill-ins` {scope: LEDGER\|VOUCHER, key, attribute: HSN\|UQC\|QTY\|POS\|..., value} (Gstr1WorkflowController:145); blank value = delete (204) | fill-in value appears in `GET .../gstr1/tables`; Accountant-only (Operator 403) | `gstr1-fill-ins` |
| GSTR-1 validate + findings | Workflow detail → Gstr1ValidationPanel / findings | `GET /api/v1/workflows/{id}/gstr1/validation` (errors/warnings), `GET /{id}/findings`, `POST /{id}/findings/{fid}/action` | `{errors, warnings}` non-null; findings array; bogus finding id rejected | `gstr1-findings` |
| GST validation (standalone) | Upload → validate | `POST /api/gst/validate` multipart file (GstValidationController:38) | 200 `{totalVouchersAnalyzed, results}`; unauthenticated rejected | `gstr1-validate` |
| GSTR-1 download | Workflow detail → download button | `GET /api/v1/workflows/{id}/gstr1/export?includeIrp=false` (Gstr1WorkflowController:201), Accountant-only, from PREPARE onward | 200 JSON containing the fill-in value; Operator 403 | `gstr1-export` |
| TDS quarter export (Form 140 / 26Q) | Workflow TDS tab → quarter prepare → export | payment-month workflows + `POST /api/v1/workflows/{id}/tds/challans` + `/challans/{cid}/approve`, TDS_26Q `GET /{id}/tds/entries`, `POST /{id}/tds/entries/map`, `GET /{id}/tds/gate`, `POST /{id}/finalize`, `GET /{id}/tds/export` (TdsWorkflowController:161-250) | FY2026 Q1 export is Form 140 (`^BH^1^3^140^`, tax year 202627, 194C PAN-derived 1023/1024, 194J_B 1027, 194T 1067, file `140_<TAN>_FY2026_Q1.txt`); FY2025 Q1 stays 26Q (94C/4JB/94T, `26Q_...`); the 194T voucher (partner remuneration, section seeded from the statutory tables) appears as a `194T` entry; 194M post-2026 → 400 "Form 141"; 194C payee without PAN → 400 "Cannot determine 194C payee type"; Operator export 403 | `tds-form140` |
| TDS section labels (both Acts) | Masters page → findings/masters table; TDS quarter table | `GET /api/v1/uploads/latest/mismatches?ruleCode=TDS_SECTION_MAPPING`, `GET /api/v1/preconfigured-masters` | masters suggestion reads `194C / 393(1) [Table: Sl. No. 6(i)]` and `194J_A / 393(1) [Table: Sl. No. 6(iii).D(a)]`; stored `tdsSection` stays `194C`; date-known screens switch at 2026-04-01 (covered by client `tdsSectionDisplay` component tests) | `masters-tds-labels` |
| TDS applicability at registration | Organization setup page → TAN + TDS-applicable capture | `POST /api/organizations` {pan, tan?, tdsTurnoverExceeded?, priorYearTurnover?, turnoverNature?} (OrganizationController) | company PAN → `deductorType:"K"`, TAN normalised+stored, `tdsApplicable:true`; individual PAN below the limit → `deductorType:"Q"`, `tdsApplicable:false`, TAN not stored even when sent; missing turnover answer / malformed TAN / missing entity type → 400 with the exact prompt; profession (50 lakh) vs business (1 crore) derived answers | `tds-applicability-registration` |
| TDS applicability API | Masters page → TDS applicability panel | `GET/PUT /api/v1/organizations/{id}/tds-applicability[/{fy}]` (TdsApplicabilityController) | GET shows `entityCode`/`entityCodeSource` + per-year rows; company PUT → 400 "always deducts"; operator PUT 403; missing `applicable` → 400; PUT true/false round-trips a DECLARED year | `tds-applicability-registration` |
| TDS gating for non-deductors | Workflows page / masters page for a non-deductor | `POST /api/v1/workflows` {TDS_PAYMENT, TDS_26Q}, `GET /api/v1/uploads/{id}/mismatches`, `PATCH /api/v1/uploads/{id}/ledgers/{sid}`, `GET /api/v1/tds/debtor-tans/missing` | TDS workflow start in a not-applicable FY → 400 "not applicable"; GSTR3B unaffected; masters upload raises no TDS_SECTION_MAPPING findings but still flags PAN_FORMAT; `tdsSection` set via the snapshot PATCH stays on `upload_ledger_snapshots` for a non-deductor (hidden, never cleared — preconfigured masters rows are seeded at first upload and not re-synced by the PATCH, UploadController:205/464); debtor-tans/missing still reports gaps; finalized TDS workflow blocks marking the year not applicable (409 "unfinalize it first"); draft TDS workflows of a not-applicable FY vanish from `GET /api/v1/workflows` | `tds-applicability-gating` |
| TDS discovery prompts + PAN-only advisories | Settings → TDS applicability prompts; daybook review → advisory panel | `POST /api/v1/compliance/baseline/confirm`, `GET /{id}/tds-applicability/prompts`, `POST .../prompts/{pid}/confirm`, `POST .../prompts/{pid}/dismiss`, `GET /{id}/tds-applicability/{fy}/pan-only-advisories` (TdsApplicabilityPromptService, PanOnlyTdsAdvisoryService) | BOOKS_EXCEED_LIMIT prompt after baseline confirm when measured preceding-FY books exceed 50 lakh, message says "since 1 April 2026"; blank dismiss reason 400; confirm → year applicable `CONFIRMED_FROM_BOOKS`; re-saving the unchanged answer leaves the confirmed baseline untouched; 194M/194-IB advisories with Form 26QD/26QC before 2026-04-01, Form 141 on/after; empty for an applicable year and for a company | `tds-applicability-prompts` |
| Statutory TDS sections (picker/label source of truth) | Masters pickers, TDS override dropdowns, quarter-prepare entry labels | `GET /api/tds/sections` (StatutorySectionController) — read-only list of the active Income-tax sections in `statutory_sections` in `sortOrder` order: `code`, canonical `description`, `legalReference` from the DEFAULT `statutory_section_rules` row covering today (the s.393 reference; equals the code itself for sections with no new-Act row, e.g. 194M), `rpu26qCode`, `rpu140Code`, `sortOrder`; 194I is served as the `194I_A`/`194I_B` halves only; 13 sections incl. the Finance Act 2025 additions 194D (94D/1005), 193 (193/1019) and 194T (94T/1067); 194M carries `393(1) [Table: Sl. No. 6(ii)]`; 194B (verified, out of scope), 194 dividend and 192A are not seeded so absent; any authenticated role allowed, anonymous 401 | `statutory-sections` |
| TDS ledger mapping | Settings → Compliance → TDS ledgers panel | `GET /api/v1/tds/ledger-mapping` (view: `complete`, `blockers`, `receivableWarnings`, candidate rows with `suggestedRole`/`suggestedSection`/`area`), `PUT` same path `{items:[{ledgerName, role: TDS_PAYABLE\|TDS_RECEIVABLE\|NOT_TDS, section}]}` (TdsLedgerMappingController:20) | duty ledgers found via the Duties & Taxes group chain with sections from their names (`TDS Payable - 194C A/c` → payable+194C, `- 194Q A/c` → payable+194Q, unseeded `- 192B A/c` → payable+null section); `TDS (FY:24-25) A/c` under Loans & Advances → receivable, area RECEIVABLE; unmapped payables refuse day-book uploads for TDS-applicable orgs (422 mentioning the TDS ledger mapping) and block TDS analysis/advance via TDS_MAPPING/TDS_LEDGER_UNMAPPED findings; GST-taxtype and EXPENSE/PURCHASE/GST-category ledgers are never candidates, and neither are unflagged GST-looking duty ledgers (CGST/SGST/IGST/GST/cess names, GST group, incl. GST-TDS `TDS - CGST Cash Balance A/c`) unless Tally marks them taxtype TDS; payable saves shrink the blocker list, a NOT_TDS save removes a candidate, once the gate is complete uploads succeed and analysis reaches FINDINGS_REVIEW (advance reaches PREPARE); unmapped receivable only warns (warn-not-block while payables are clean) and clears on save with the row marked saved (`savedBy`/`savedAt`); Accountant-only PUT (Operator 403); unknown ledger / section on a non-payable role → 400 | `tds-ledger-mapping`, `tds-ledger-mapping-gst-exclusion` |
| GST tax-ledger mapping daybook gate | Settings → Compliance → GST tax ledgers panel; day-book upload (workflow detail) | `GET /api/v1/gst/tax-ledger-mapping` (view: `complete`, `blockers`, `gstApplicable`, rows with `suggestedRole`/`suggestedHead`), `PUT` same path `{items:[{ledgerName, role: OUTPUT\|INPUT\|CASH_BALANCE\|LIABILITY_BALANCE\|CREDIT_BALANCE\|GST_TDS\|NOT_TAX, head}]}` (TaxLedgerMappingController) | for a GSTIN org (gstApplicable true) an unsaved/incomplete mapping refuses day-book uploads with 422 naming the GST tax-ledger mapping (unmapped GST-categorized ledgers, then the 6 areas × IGST/CGST/SGST heads); a full area×head save completes the gate so the same upload succeeds; non-GSTIN orgs (gstApplicable false) upload freely even with unmapped GST ledgers; both TDS and GST messages appear together when both gates are incomplete | `gst-ledger-mapping` |
| Portal-upload record | Workflow detail → record portal upload | `POST /api/v1/workflows/{id}/gstr1/portal-upload` {fileHash, note} (Gstr1WorkflowController:179) | `{recorded: true}` | `filed-returns-import` |
| Filed-return JSON import | Filed-returns page → import GSTR-1 JSON | `POST /api/v1/filed-returns/gstr1/json` multipart file + form=GSTR1 (FiledReturnController:57), `GET /api/v1/filed-returns/snapshots` | 201 snapshot id; id present in snapshots list | `filed-returns-import` |
| GSTR-1 B2CL dated threshold | Prepare tables vs filed-return recon for an inter-state B2C invoice near the threshold | `GET /api/v1/workflows/{id}/gstr1/tables`; `POST /api/v1/filed-returns/baseline/{id}/reconcile` for Jul/Aug 2024 baseline rows | a Rs 1,50,000 inter-state B2C invoice is B2CS in July 2024 (2.5 lakh) and B2CL from August 2024 (1 lakh); prepare tables and recon both show that split and recon returns RECONCILED with material 0 | `gstr1-b2cl-threshold` |
| Filed-return missing baseline | Filed-returns page → import for a period without a baseline | `POST /api/v1/filed-returns/gstr3b` period without baseline (FiledReturnImportService matchBaselineRow) | 409 message names the month and says to create a baseline in Settings > Baseline periods | `filed-returns-import` |
| Tally write-back (PAN) | Masters page → Tally changes tab → export/retry | `GET /api/v1/tally-changes`, `POST /api/v1/tally-changes/export` {itemIds?, confirmStale?}, `POST /api/v1/tally-changes/{id}/retry` (TallyChangeController); PAN_FORMAT findings acknowledged via `/api/v1/uploads/{jobId}/findings/{fid}/action` with `{action:"ACKNOWLEDGE", value:"<PAN>"}` or `{action:"ACKNOWLEDGE", noPan:true}` | acknowledged PAN (or No PAN) becomes a PENDING/EXPORTED item; export is a JSONEx file with `static_variables[svMstImportFormat]=jsonex`, `Alter` ledger messages, and `incometaxnumber` (empty string clears the PAN); re-upload with a different PAN marks EXPORTED items FAILED/TALLY_VALUE_CHANGED (retry → PENDING), target PAN/empty PAN marks them APPLIED, then export returns 409 NOTHING_ELIGIBLE; Operator export/retry 403 | `tally-writeback` |
